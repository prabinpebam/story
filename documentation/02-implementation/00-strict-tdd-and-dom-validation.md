# Strict TDD + Functional DOM Validation (Implementation Plan)

## Purpose
This document is a non-negotiable reference for implementing features using a **strict TDD loop** backed by **rigorous functional tests** and **frontend DOM/UI validation** for every incremental change.

## Non-Negotiables (Read Before Coding)
- **No production code without a failing test first** (Red → Green → Refactor).
- **Every increment must have functional coverage** (Playwright) for the user-visible outcome.
- **DOM/UI validation is required** for each increment:
  - assert user-facing text/content,
  - assert key DOM attributes/state (classes, ARIA, `data-*`),
  - assert interaction results (focus, selection, disabled/enabled, visibility),
  - assert geometry/layout only when it’s the requirement.
- **No flaky tests**: deterministic data, deterministic time, deterministic rendering assumptions.
- **One increment == one commit-sized unit** (even if you squash later): tiny, reviewable, test-backed.

## Definition of “Increment”
An increment is the smallest behavior change that:
- is observable in the UI/DOM (or a user action path),
- has a clear acceptance condition,
- can be tested end-to-end in isolation.

## Required Test Pyramid (Strict)
1) **Functional tests (required for every increment)**
   - Framework: Playwright.
   - Scope: user action → app behavior → DOM/UI assertions.
   - Must verify: visible result + state changes + error/edge handling relevant to the increment.

2) **Unit/integration tests (required when logic exists)**
   - Framework: Vitest.
   - Scope: parsing, mapping, transforms, reducers, validation, deterministic utilities.
   - Must verify: pure logic rules and corner cases.

Rule: if the increment adds logic that can break without UI changes, add Vitest coverage too.

## The Strict TDD Loop (Per Increment)
1. **Write the test first (RED)**
   - Add/extend a Playwright spec that fails for the new behavior.
   - Add Vitest tests first for any new logic.

2. **Run the smallest test set**
   - Prefer targeted execution: single Playwright spec and/or single Vitest file.

3. **Implement the minimum production code (GREEN)**
   - Do the smallest change that makes the new test pass.
   - Avoid refactors while still red.

4. **Refactor with tests green (REFACTOR)**
   - Improve structure, remove duplication, tighten types/contracts.
   - If refactor requires behavior change, treat it as a new increment.

5. **Add negative/edge assertions**
   - One or two high-value edge cases per increment (not a matrix).

6. **Run the functional suite for the area**
   - Ensure no regressions in nearby flows.

## DOM/UI Validation Rules (Functional Tests)
Use explicit, readable assertions. Avoid overfitting to markup that isn’t part of the contract.

Required assertions per increment:
- **Visibility/Presence**: element exists and is visible when expected.
- **Content**: text, label, or accessible name.
- **State**: selected/active/disabled, aria attributes, or class toggles that represent state.
- **Interaction**: clicking, typing, dragging, keyboard shortcuts, clipboard actions, etc.

Allowed UI assertions (choose the simplest that proves the behavior):
- `toBeVisible`, `toHaveText`, `toHaveValue`, `toHaveAttribute`, `toHaveClass` (carefully), `toBeEnabled/Disabled`.
- CSS/layout assertions only when required by spec (keep to a minimum).

Selector strategy:
- Prefer **role/name** queries (accessibility-first).
- Use `data-testid` only when role/name is unstable or ambiguous.
- Never rely on brittle selectors (deep nesting, autogenerated class names).

## Determinism & Flake Prevention
- Freeze time when time matters.
- Avoid network dependency; stub or use deterministic fixtures.
- Avoid animation timing dependence; disable animations in tests where possible.
- Use stable test IDs only for stable UI contract points.

## Test Data & Fixtures
- Keep fixtures small, readable, and versioned.
- Every fixture must have a clear intent and minimal surface area.
- Prefer “golden” expectations only when stable and intentionally canonical.

## CI/Review Gates
A change is not “done” unless:
- new behavior is covered by Playwright functional tests,
- new logic is covered by Vitest tests (when applicable),
- tests are deterministic and pass locally,
- no skipped tests unless explicitly approved and tracked.

## Pull Request Checklist (Mandatory)
- [ ] At least one new/updated Playwright test proving the increment.
- [ ] DOM/UI assertions validate user-visible behavior and state.
- [ ] Added Vitest coverage for new logic (if any).
- [ ] No reliance on brittle selectors or timing hacks.
- [ ] Increment is small and focused; no unrelated refactors.

## Escalation Rule
If an increment cannot be expressed as a deterministic functional test, stop and adjust the design/spec until it can.
